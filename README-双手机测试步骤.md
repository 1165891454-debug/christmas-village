# Omo's Christmas Village — 阶段 1 双手机同步测试指南

## 这个测试页做什么

在开发完整游戏之前，用最小成本验证整个项目最关键的假设：**两部 iPhone 能否稳定共享同一个游戏世界**。包含：房间创建/邀请加入、玩家 A/B 绑定、共享圣诞树（4 阶段）、换装（3 套）、实时同步、刷新持久化、断线提示与重连。

技术方案：纯前端页面 + Firebase Realtime Database（实时推送，免费额度足够）+ Firebase Hosting（免费 HTTPS）。没有任何付费服务。

## 你需要手动做的事（总共两件事）

### 事 1：创建 Firebase 项目并拿到配置（约 5 分钟，只需做一次）

1. 打开 https://console.firebase.google.com/ ，用 Google 账号登录 → 「创建项目」
   - 名称随意（如 `omo-christmas`）；Google Analytics 选「停用」
2. 左侧 Build → **Realtime Database** → 「创建数据库」
   - 地区选 **Singapore (asia-southeast1)**（离中国最近）；模式选「以测试模式启动」
3. 左侧 Build → **Authentication** → 「Get started」→「Sign-in method」标签
   → 找到 **Anonymous（匿名）** → 点启用 ✅（安全规则需要登录身份，但不需要你注册任何账号）
4. 左上角齿轮 →「项目设置」→「常规」→ 底部「你的应用」→ 点 `</>` 图标添加 Web 应用
   → 复制给出的 `firebaseConfig`，**替换 `firebase-config.js` 文件里大括号中的内容**并保存
5. Realtime Database →「规则」标签页 → 删除原有内容，粘贴下面「安全规则」一节的内容 → 「发布」

> 💡 更省事的做法：把第 4 步复制的配置直接发给我（在对话里粘贴即可），我来替你填好并重新打包，你就不用碰代码文件了。

### 事 2：把网页发布到 HTTPS（已按网络实测选择推荐方案）

> 📶 **网络实测结果（2026-10-23，本机真实测试）**：Firebase 的认证、数据库域名全部可达 ✅；但 Firebase Hosting 的 `web.app` 域名不可达 ❌；Cloudflare 控制台不可达 ❌；腾讯 EdgeOne Pages 可达 ✅。因此推荐腾讯方案，Firebase Hosting 仅作备用。

**方式 A（推荐）：腾讯 EdgeOne Pages，浏览器拖拽上传，全程中文、无需装任何软件**

1. 先把精简上传包 `网站上传包-EdgeOne.zip` 准备好（随项目一起提供；如果拿不到，用 WinRAR/右键压缩 `christmas-village` 文件夹也行）
2. 打开 https://pages.edgeone.ai/zh/ ，把 ZIP 拖进去 → 点击部署 → 得到 `https://xxx.edgeone.app` 的 HTTPS 链接
3. 建议注册一个账号（微信扫码即可，免费）后再上传——不注册也能先用，但登录后才能长期管理和更新链接
4. 免费额度完全够用；**如果过程中出现任何要求绑卡/付费的提示，停下来告诉我，不要继续**

**方式 B（备用）：Firebase Hosting——需要电脑装 Node.js，双击 `deploy.bat`**

⚠️ 实测 `web.app` 域名在当前网络不可达，**仅当你换了网络环境（如 VPN）或手机实测可达时再用**。步骤：双击 `deploy.bat` → 输入 Firebase 项目 ID → 浏览器登录 Google → 等待 `[OK] Done!`。

## 安全规则（Realtime Database →「规则」页粘贴这段）

> ★ v2.0.0 更新：新增了 `world` 节点（共享进度：资源/花园/回忆/任务/热可可）。**如果你之前粘贴过旧规则，必须重新粘贴这一版并「发布」，否则共享进度只会存在本机（游戏里会有黄色提示）。这是 v2 唯一需要你手动做的事。**

```json
{
  "rules": {
    "rooms": {
      "$roomId": {
        ".read": "auth != null && $roomId.length >= 6 && $roomId.length <= 32",
        "slots": {
          "$slot": {
            ".write": "auth != null && ($slot === 'a' || $slot === 'b')"
          }
        },
        "tree": {
          ".write": "auth != null && (root.child('rooms/' + $roomId + '/slots/a/uid').val() === auth.uid || root.child('rooms/' + $roomId + '/slots/b/uid').val() === auth.uid)"
        },
        "world": {
          ".write": "auth != null && (root.child('rooms/' + $roomId + '/slots/a/uid').val() === auth.uid || root.child('rooms/' + $roomId + '/slots/b/uid').val() === auth.uid)"
        },
        "log": {
          ".write": "auth != null && (root.child('rooms/' + $roomId + '/slots/a/uid').val() === auth.uid || root.child('rooms/' + $roomId + '/slots/b/uid').val() === auth.uid)"
        },
        "presence": {
          "$slot": {
            ".write": "auth != null && ($slot === 'a' || $slot === 'b') && root.child('rooms/' + $roomId + '/slots/' + $slot + '/uid').val() === auth.uid"
          }
        }
      }
    }
  }
}
```

**这套规则做到了什么（如实说明）**：

1. **所有访问必须匿名登录**——没有身份的脚本/爬虫一个字节都读不到写不了；
2. **房间 ID 是 10 位随机码**，未拿到邀请链接的人连房间都找不到；
3. **知道链接的人可以进入并选择/接管角色**（页面在满员时会显示「以玩家 A / 玩家 B 进入」按钮）——这是有意设计：链接只在你和她手里，这样即使清缓存、换手机、用无痕模式，也永远不会再被锁在门外；
4. **圣诞树、日志、在线状态只接受已占用槽位的玩家写入**，其他访客只能看。

剩余风险（如实告知）：任何拿到邀请链接的人都能占用角色并操作游戏。对一个只有你们两人持有链接的私人礼物，这是合理的取舍；请像保管两人合照一样保管这条链接。

## 第三步：双 iPhone 测试（按此清单逐项打勾）

两部 iPhone（iOS 26）都打开 Safari，访问上面的 HTTPS 链接。

| # | 测试项 | 操作 | 预期 |
|---|--------|------|------|
| 1 | 创建/加入 | 手机 A 点「创建我们的房间」→ 复制链接发给手机 B（微信即可）→ 手机 B 打开链接 | 两部手机显示同一个房间码 |
| 2 | 身份绑定 | 看两部手机「我的角色」卡片 | 一部玩家 A，一部玩家 B，刷新后身份不变 |
| 3 | 树同步 | 手机 A 连点「装饰圣诞树」两次 | 手机 B 的树实时变化，日志出现记录 |
| 4 | 服装同步 | 手机 B 换「圣诞装」 | 手机 A 的对方卡片实时变为圣诞装 |
| 5 | 持久化 | 分别刷新、杀掉 Safari 重新打开链接 | 树阶段、服装、日志全部还在 |
| 6 | 第三人防占用 | （可选）第三台设备/无痕窗口打开同一链接 | 显示「这个房间已经有两位玩家啦」 |
| 7 | 断线提示 | 手机 A 开飞行模式几秒再关闭 | A 出现红色断线横幅；恢复后自动重连 |
| 8 | 添加到主屏幕 | Safari 分享 →「添加到主屏幕」→ 从图标打开 | 独立窗口打开，同步正常 |

连接状态：顶部绿点=已连接云端，红点+横幅=连接中断。「对方角色」卡片显示对方在线/离线。

**测试注意事项**：测试「第三人防占用」或重新绑定身份时，用页面底部的「清除本机绑定并重新进入」按钮，它会重置本机的匿名身份。

## 玩法闭环（一天 5-10 分钟的节奏）

1. **每天进温室** → 自动领当日补给（种子×2、木材×1、鲜花×1）
2. **种花（30 分钟）/ 种树（6 小时）** → 睡一觉、上个班回来收获
3. **小镇里找闪光的回忆挂饰**（16 处，每段新回忆 +1 颗种子）→ 菜单里随时翻「📖 旅行回忆册」
4. **工坊做手工礼物**（木头小鸟/八音盒/星星挂饰，需要木材+鲜花）
5. **材料够了回广场装饰圣诞树**：3 木 → 已装饰；+6 木 6 花 → 彩灯；+5 木 8 花 2 礼物 → 全亮
6. **咖啡馆每天一杯免费热可可**（就是来暖一下的小仪式）
7. **2026 年 12 月 25 日**，两人站在全亮的树下 → 圣诞夜结局 + 圣诞合影（按你们的实际进度构图）

## 唯一的手动步骤（重要）

把上面更新过的**安全规则**（含 `world` 节点）粘贴到 Firebase 控制台 → Realtime Database → 规则 → 发布。没做这步游戏照样能玩，但进度只存在各自手机里（会有提示），换设备/换账户时进度带不走。

## 测试模式

在网址后面加 `?dev=1`（例如 `https://.../?room=xxxx&dev=1`）：生长变成 6-10 秒、日期门放开，方便你在 12 月 25 日之前完整跑一遍流程。正式玩不要带这个参数。

## 换账户 / 换设备衔接指南（如果需要在新账户下继续开发）

进度本身不怕换账户：**所有游戏进度都在 Firebase 云端房间里，不绑在 GitHub 账户上**。换账户时只有「托管代码的地方」要搬家：

1. **游戏数据**：在新设备/新账户打开游戏，用同一个房间码或邀请链接进入即可——匿名身份会自动重新认领角色，云端进度（资源/花园/回忆/树/任务）原样加载。
2. **代码搬家**：本地 `christmas-village/` 文件夹整个复制（U 盘/微信文件传输都可以），或在新账户建一个新 GitHub 仓库，网页上传全部文件（和之前一样的流程），再开 GitHub Pages。
3. **Firebase 不用动**：firebase-config.js 里写的是 Firebase 项目配置，与 GitHub 账户无关，照常工作。
4. **换手机玩**：不用任何操作，打开邀请链接，满员时点「以玩家 A/B 进入」接管自己的角色。
5. 详细的开发交接文档见 `PROJECT_HANDOVER.md`（文件职责/架构/数据模型都写在里面，给任何 AI 或开发者都能接手）。
